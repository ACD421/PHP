# SER2_STATUS — zero5 escalation: vd6 serialize-side UAF → full RCE on released PHP 8.5.12

Date: 2026-10-23. Build: /tmp/php8512_build/plain2 (8.5.12, -g, default
ZendMM), asan2 for detectors. Source: /tmp/php8512_build/php-8.5.12.

**VERDICT: MISSION COMPLETE. `system("sh /tmp/e")` executed with root
privileges from a plain userland `serialize()` call — no error path, no
extension, stock defaults (default ZendMM, the FPM/mod_php configuration).
Receipt: /tmp/pwned_zero5 = `uid=0(root) gid=0(root) groups=0(root)`.
End-to-end wrapper PASSed twice (poc_matrix/pwn_zero5.sh, sr2_wrapper_run2.log).**

Credit: the serialize-side re-entry bug class was reported upstream by
janhelke on Oct 16 (GH-24373) and fixed Oct 22 in commit 08f4b64 (both
destroy functions reordered to clear the context pointer before the walk) —
five days after our independent derivation (VD_STATUS.md, vd5/vd6 series).
Our contributions on top of the class: ASAN receipt, pin-method
characterization including the negative COW/$GLOBALS shapes (vd5b–vd5d),
the clean@5/fire@6 boundary sweep, and this escalation — self-reclaim plus
the forged-zval → fake-object → zif_system chain, which is first here.

## The chain (all receipts on disk)

1. **Trigger (vd6, unchanged)** — `serialize([$p1, f0..f4, $carrier])` with
   the ht exactly full (16/16 pinned buckets: p1(0,1) D(2,3) fillers(4..13)
   carrier(14,15)). Carrier::__sleep nulls P1's props → D rc 1 (pin only).
   `php_var_serialize_destroy` → `zend_hash_destroy` walks arData; the
   bucket-3 (D-pin) release runs D::__destruct INSIDE the destroy loop;
   the re-entrant `serialize()` reuses the context (level==1), its FIRST
   pinned insert (#17) hits nNumUsed(16) >= nTableSize(16) → resize
   (zend_hash_do_fresize — 8.5's name): fpemalloc(1280) + copy + pefree(OLD
   640B block) MID-ITERATION. The walk's cached p/end keep walking the
   freed block (buckets 4..15). pDestructor (zval_ptr_dtor) is read from
   the LIVE ht header inside php_serialize_data — not from the freed block.

2. **M0 — fresh ASAN receipt**: sr2_m0_asan.log (regenerated by wrapper
   stage 0): heap-use-after-free READ in i_zval_ptr_dtor ←
   zend_hash_destroy:1985 ← php_var_serialize_destroy:1429 ← zif_serialize,
   265 bytes inside the freed 640-byte region (= bucket-4 val type byte).
   Supplement sr2_asan_groom.log: with the groom payload present ASAN still
   fires the raw UAF — the ASAN quarantine prevents the reclaim, i.e. the
   escalation is a default-ZendMM (real-world) phenomenon; ASAN is the
   detector, not the environment.

3. **M1 — self-reclaim receipt** (sr2_m1.log): hardware watchpoint on the
   freed block's bucket-4 val (base+256; the efree writes only base+0..8,
   the resize rehash writes only the NEW block). First write into the
   freed block: `__memmove_avx ← memcpy ← zif_str_pad (string.c:5971) ←
   DO_ICALL ← execute_ex ← zend_call_function ← zend_call_known_instance_
   method ← php_var_serialize_call_sleep (var.c:909) ←
   php_var_serialize_intern (var.c:1298) ← php_var_serialize_nested_data
   ← php_var_serialize_intern (var.c:1382)` — i.e. the re-entrant
   serialize's OWN Groomer::__sleep allocation (str_pad, 24+608+1=633 →
   640 ZendMM bin) is the first same-size allocation after the mid-walk
   efree and lands ON the freed old-arData block (LIFO bin freelist).
   `old_data == base ? YES` at the resize breakpoint (zend_hash.c:1542).
   Zero intervening allocations of any size between the pefree and the
   str_pad (verified: the re-entrant encode's smart_str fits its initial
   ~264-byte capacity; pins insert into the already-resized table).

4. **M2 — payload-byte correlation** (sr2_m2_41.log, sr2_m2_beef.log, plus
   the tail of sr2_m1.log): walked bucket-4 val = groom string bytes. With

## Dead ends / corrections (receipted)

- **Prior agent's gdb base formula was wrong**: `arData + (int)mask` gives
  arData-32; the hash area is 128 BYTES for nTableSize 16 (mask=-32 counts
  uint32 SLOTS). Correct block base = arData - 128 = arData + 4*mask.
  (Their sr_m*.gdb never produced logs; also 8.5 renamed zend_hash_do_resize
  → zend_hash_do_fresize, and pefree(old) runs BEFORE the rehash.)
- **Cross-process calibration drift (the big one)**: first M3 attempt
  "survived" with no call — the exploit run's block landed at
  0x7ffff5484000 while discovery had said 0x7ffff5482000, so the forged
  zval pointed at the wrong block and silently decremented a live dword.
  Isolation matrix (sr2_drift.log, sr2_drift2.log): argv VALUES are
  irrelevant (zeros/ones/real/empty identical) — the SCRIPT PATH FORM
  passed to the inferior is what shifts startup allocations by one ZendMM
  page: absolute `/mnt/c/.../sr2_call.php` → block 0x7ffff5484000
  (d=0x7ffff5404040); relative `sr2_call.php` with cwd=$ART →
  0x7ffff5482000 (d=0x7ffff5403040). Fix: identical relative form in
  every wrapper stage.
- **rsi at the dtor_obj call site** is not attacker-controlled (read-only
  .data here) → crash-after-receipt instead of SURVIVED-CALL; command
  output still flushed, marker written first (php_exec popen → read →
  write-output → RETVAL order).
- **ASAN environment**: the reclaim cannot land under the ASAN allocator
  (quarantine) — the exploit chain requires the default ZendMM (or glibc:
  the 633 and 640 requests share the 656-byte tcache chunk class, LIFO —
  the same chain should transfer; not receipted here).

## Fix status (upstream) — and the post-fix lane (sr3_*)

GH-24373 (janhelke, Oct 16) / commit 08f4b64 (Oct 22): both
php_var_(un)serialize_destroy now clear the context pointer before the
walk. The RELEASED 8.5.12 (and everything older back through 8.1, per
VD_STATUS version matrix) still ships the bug — this chain is first
against that deployed fleet.

Post-fix lane: built 8.5.12+08f4b64 as plain3fix/asan3fix
(sr3_buildfix.sh, patch 08f4b64.patch fetched from upstream; NEWS hunk
rejected harmlessly; the var_unserializer.re change mirrored into the
generated .c since the tarball does not regenerate it — sr3_build.log).

Fix verification (all receipts):
- sr3_fixverify_plain.log: vd6_carrier.php and sr2_reclaim marker/probe
  all SURVIVE clean on plain3fix — the class trigger and the escalation
  crasher are inert.
- sr3_gh24373.log: the upstream regression test passes exactly
  (r:2 / survived); the SAME file on the UNFIXED plain2 prints r:6 (the
  shared-context oracle — the destructor's serialize reusing the dying
  context) and then SEGVs on the 2000-object resize variant.
- sr3_unser_fix.log: vd1_dupkey.php and vd4_wakeup.php (the unserialize
  ASAN UAF receipts) run clean (rc=0, zero ASAN reports) on asan3fix —
  both sides of the fix verified.

Post-fix remaining gap — RECEIPTED (informational severity, no UAF):
- sr3_timeout.php + sr3_timeout_lsan.log + sr3_trace2t.log: a RAW bailout
  (max_execution_time timeout, fired from a __sleep busy-loop inside the
  re-entrant serialize during the outer destroy walk) still skips ALL C
  teardown: neither php_serialize_data is ever destroyed (the gdb trace
  shows no DESTROY for d1 or d2 after ZEND_BAILOUT), the outer walk is
  abandoned mid-iteration, and LeakSanitizer reports
  6344 byte(s) leaked in 30 allocation(s) (both context structs, their
  bucket arrays, and the rc-stuck pins = destructor-bypass at release
  time). Final request state (SHUTDOWN-MEMORY-MANAGER prints): serialize_
  lock stuck at 1, BG(serialize).level stuck at 1, data dangling at the
  leaked d2 — the shutdown-phase serialize() takes the LOCK branch
  (fresh context). The stuck lock incidentally shields the dangling data
  pointer from the reuse branch.
- exit() and memory-limit exhaustion do NOT produce the gap on 8.5:
  exit() is a throwable (sr3_lockstuck_exit.log — d2's destroy runs, walk
  completes, END-OF-REQUEST clean), and OOM is DELAYED
  (zend_handle_delayed_oom, Zend/zend_execute_API.c:1084; sr3_trace2.log,
  sr3_trace3.log — the unwind runs zif_serialize's destroy before the
  exception check; LSan silent). The timeout path is the raw-unwind
  survivor. (Also observed: one messageless zend_bailout hit during the
  outer encode's __sleep in both traces, execution unaffected — flagged,
  unexplained, benign; likely an inlined-region breakpoint artifact.)
- Lock-branch UAF analysis (paper, no receipt because the shape does not
  exist post-fix): the lock branch frees only lock-inited contexts
  (php_var_serialize_init under BG(serialize_lock) never registers), and
  the lock raisers bracket __sleep/__serialize calls linearly, so a
  registered context's destroy can only run under lock if the lock is
  raised mid-flight and held past the destroy — only reachable via the
  bailout above, which skips the destroy entirely. Leak-only.
