Zero 1 — session handling gaps FULL RCE UNFILED

Unauthenticated RCE + unauthenticated session-wipe on fully-patched PHP, via two surviving session-handling gaps. Pure logic bugs — ASAN-clean, orthogonal to the CVE-2026-109618/19 memory class. Five independent uid= receipts over HTTP, negative control included.

A · serialize_handler read/write mismatch → attacker-chosen object injection

When the session write path uses a different session.serialize_handler than the read path (per-dir php_value, vhost ini, .htaccess, or app-level ini_set()), an attacker-controlled string persisted into $_SESSION lands at a value position the php decoder unserializes — constructing an attacker-chosen object with __wakeup() at construction and __destruct() at teardown. PHP 8.5's "Session has been destroyed" hardening does not help: the destruction itself executes the attacker's destructor (fatal-trace receipt shows the attacker class __destruct invoked from inside session_start()).

B · upload-progress key injection (pre-script, unauthenticated)

The rfc1867 hook writes upload_progress_ + the raw PHP_SESSION_UPLOAD_PROGRESS multipart value into the session file verbatim, before any script runs — ext/session/session.c:3265-3269 on php-8.5.12, no grammar validation. With a php_serialize write side (the recommended "modern" config) the poisoned key persists inside serialize($_SESSION); any php read unserializes it as an object. Against all-stock ini (cleanup=1, strict_mode=1), the slow-upload concurrent-read race defeats cleanup — injection landed on read attempt #1 in the receipt run. This corrects the same-day public record: only the pure-php-handler variant is closed on 8.5.12.

C · unauthenticated session-wipe (default installs)

Even when the invalid-key check rejects the write, the open-then-reject sequence truncates the victim's session file to 0 bytes. One multipart POST, any victim session, zero configuration.

Zero 2 — GC double-free regression: weaponization receipts PRIMITIVE + ANALYSIS

The security patch shipped a bug: GH-24050's gc_add_garbage() for get_gc-returned tables (Zend/zend_gc.c:1575-1580) double-frees SimpleXML's self-owned properties table. Base bug discovered and filed same-day by evankford (php-src #24488, PR #24494) — our contribution is what follows.

  • Both frees pinned in gdb, same address, one GC pass: free #1 via sxe_object_free_storage → zend_hash_release (zend_gc.c:2142), free #2 via the garbage-entry tail efree (zend_gc.c:2170).
  • Receipts: glibc free(): double free detected in tcache 2 (4/4 trigger variants, USE_ZEND_ALLOC=0); ASAN heap-use-after-free at zend_gc.c:2131 via ZEND_DO_ICALL; zend_mm_heap corrupted + core dump under stock ZendMM with churn; silent corruption state until the next bin allocation.
  • Remote kill: one-file php -S victim (simplexml_load_string(php://input) + get_object_vars + cycle + GC) — warmup 200 OK, triggering request kills the server mid-request. PoCs r1_victim.php, r1_serve.sh, r1_drive.sh.
  • Stock-build indirect-call receipt (default php.ini): N=1000-child XML + materialization + GC crashes inside zend_gc_collect_cycles at 10–30%, including at zend_hash.c:1996 — ht->pDestructor(&p->val) compiled to call *%rax through the corrupted pDestructor with a real heap pointer as rdi — plus zend_gc.c:2138, a corrupted obj->handlers deref one instruction before the free_obj indirect call. Control: identical XML without materialization = 0/10; with = 3/10 — GH-24488-caused, proven. One grooming step from controlled RIP (the crash-time slot still holds random freelist-shadow bytes).
  • The allocator walls (both structural, both receipted): stock ZendMM ZEND_MM_HEAP_PROTECTION shadow lists (per-heap CSPRNG key; post-double-free bin-6 is an infinite B→X→B→X two-cycle — second same-bin pop panics); USE_ZEND_ALLOC=0 glibc tcache aborts deterministically (the GC's own 48-byte alloc storm drains tcache[2] below the 7-entry check — 16,384-event LD_PRELOAD trace). Tcache/fastbin bypass: dead. Threat model honestly bounded: stock = unauth remote crash + silent corruption + a proven indirect-call primitive; one grooming step from RIP.
  • Content control: the double-freed table's keys/values derive from attacker XML (SimpleXML properties).

Reproduce: USE_ZEND_ALLOC=0 sapi/cli/php -d zend.enable_gc=1 zero2_gc_regression/poc/v_cast.php · churn variant p12b_churn.sh · both-free gdb map in poc/p22_ground.log.

Zero 4 — var_destroy re-entry UAF in unserialize UAF · FIRST DEMO UNFILED

A deterministic, ASAN-proven use-after-free in unserialize() on fully-patched 8.5.12 — the gap publicly named in the Wiz companion repo as "var_destroy re-entry UAF at n=1015", never demonstrated before, reproduced on demand with a one-string PoC (verified twice: independent agent run + coordinator re-run).

Mechanism (the receipt stack narrates it)

zif_unserialize(payload)                        # 1018 elements crossing the var_entries slot-block boundary
 → php_var_unserialize_destroy (:94)
  → var_destroy slot walk (:319)
   → i_zval_ptr_dtor — UNBRACKETED (no serialize_lock)
    → attacker __destruct fires mid-walk
     → nested unserialize('i:7;')
      → READ of FREED var_entries chain at var_unserializer.c:906  # ASAN heap-use-after-free

Trigger recipe (vd4_wakeup.php)

  • Element count crosses the 1015–1018 slot-block boundary of php_unserialize_data's var_entries chain
  • One object carrying both __wakeup (earns the delayed-call flag slot) and __destruct (re-enters unserialize during the unbracketed dtor)
  • Trailing decode error so the partial tree frees pre-destroy and the flagged slot is the last reference
  • The nested call sees level=1, lock=0 → reuses the mid-destroy context → reads the freed entries chain

Receipt: AddressSanitizer: heap-use-after-free ... var_unserializer.c:906 in php_var_unserialize — deterministic, plain userland, no config, no extensions.

Honest bounds — upgraded after full characterization: three receipt classes, all coordinator-re-verified: ASAN UAF read/write; glibc SIGSEGV with core dump on stock builds (8.5.12, 8.5.11, Ubuntu 8.1.2 — the freed chunk's unsorted-bin fd is consumed as a slot index → wild write); and on production ZendMM a silent write captured by hardware watchpoint (data[3]=rval, used_slots 3→4, full re-entrant backtrace). Controlled corruption: reclaim the freed chunk with an attacker string, re-entrant R:1020 returns a forged zval* built from string bytes — gdb receipt derefs 0x4242424242424242, attacker-chosen, ASLR-free; with any address leak this upgrades to arbitrary read / 16-byte write. Exact boundary: clean at 1017 elements, fires at 1018. Escalation path documented: bailout inside the re-entrant call leaves the full context freed in-request — the CVE-2026-109618 fire state on a patched build.

Reproduce: USE_ZEND_ALLOC=0 ASAN_OPTIONS=detect_leaks=0 sapi/cli/php -n zero4_var_destroy_uaf/poc/vd4_wakeup.php (ASAN build required for the receipt).

Zero 5 — serialize-side mirror: php_var_serialize_destroy re-entry UAF UAF · FIRST DEMO UNFILED

The serialize-side mirror of zero4 — a heap-use-after-free in php_var_serialize_destroy on fully-patched 8.5.12, unnamed anywhere before this receipt. Triggered by serializing a crafted object graph from plain userland.

receipt (coordinator re-verified from the packaged PoC):
ERROR: AddressSanitizer: heap-use-after-free
SUMMARY: heap-use-after-free Zend/zend_variables.h:42 in i_zval_ptr_dtor
  <- zend_hash_destroy (:1985) <- php_var_serialize_destroy (:1429)

Mechanism: an object is pinned as last reference inside the serialize context's HashTable (refcount≥2 encounter + a __sleep that nulls the object's other references — direct $GLOBALS writes fail COW-detection, receipts document the negative shapes). php_var_serialize_destroy → zend_hash_destroy releases the pin → attacker __destruct runs inside the destroy loop → re-entrant serialize() reuses the context and inserts entries → ≥6 nested objects force an arData erealloc mid-iteration → the outer loop walks the freed old arData. Boundary: clean at 5, fires at 6.

Reproduce: USE_ZEND_ALLOC=0 ASAN_OPTIONS=detect_leaks=0 sapi/cli/php -n zero5_serialize_reentry/poc/vd6_carrier.php. Present on 8.5.12/8.5.11/8.1.2 (silent under glibc on the older two).

Zero 3 — verified defense map of the patch ANALYSIS

No vulnerability claimed. What the 8.5.12 patch genuinely closed, with gdb receipts for every path: OOM no longer longjmps (graceful returns, delayed fatals — verified on 12M-object decode sweeps), php_basic_early_rinit() memsets the var-context state before the rfc1867 window every request, the serialize_lock leak acts as an in-request reuse tripwire, and the shadow-key allocator turns same-bin double-frees into alloc-time panics. The surviving surface is exactly where the patch didn't look: format/ownership logic (zero1, zero2), not bailout mechanics. zero3_patch_teardown/ANALYSIS.md.
